# 결재선 (기안·검토 절차)

품의서, 결과보고서가 함께 쓰는 결재 절차입니다. 절차는 이 파일 한 곳에만 적습니다. 각 서식의 SKILL.md는 이 파일을 가리킵니다.

- 결재 문서 = 데이터 파일(JSON) 하나 + 그 파일을 올린 Origin PR 하나입니다. DB는 없습니다.
- 승인·반려는 결재선의 검토자가 Origin PR 리뷰로 합니다. 기안한 에이전트는 리뷰를 제출하지 않습니다.
- 머지 권한: main 머지는 결재선 마지막 칸의 사람(최종 결재자)만 합니다. 전결이 있어도 전결 칸은 승인으로 결정하고, main 머지는 마지막 칸의 사람이 집행합니다. 봇과 에이전트는 main을 머지하지 않습니다. `stage/*` 브랜치로의 중간 머지는 취합이며 결재가 아닙니다. 누가 전결할 수 있는지와 취합을 누가 하는지는 그 조직의 운영규칙을 따릅니다.
- 코드: `approval.py`(결재선 검사, 리뷰 연결, 현재 차례, 머리·결재란 그리기, 렌더 실행), `approval.css`(결재란 도장 칸), `rules.json`(규칙 값의 사본. 원본은 `operating-rules-config.json`).

## 결재선 데이터

데이터 파일의 `approval.steps`가 결재선입니다. 왼쪽(아래 직급)부터 오른쪽(위 직급) 순서입니다.

```json
"approval": {
  "steps": [
    {"role": "기안", "title": "담당", "name": "홍길동", "date": "2026-10-31"},
    {"role": "검토", "title": "검토자", "name": "이가상", "reviewer": "lee@example.com"},
    {"role": "결재", "title": "최종 결재자", "name": "김가상"}
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `role` | `기안`, `검토`, `결재` 중 하나. 첫 칸만 `기안`, 마지막 칸은 `결재`, `검토`는 1칸까지이고 결재 앞에 둡니다. |
| `title` | 칸 위에 적는 칸 이름. 그 조직의 결재선에 있는 값을 그대로 씁니다(예: 담당, 검토자, 최종 결재자). |
| `name` | 그 칸 사람 이름 |
| `date` | 기안 칸에만 씁니다(필수, `YYYY-MM-DD`). 다른 칸 날짜는 Origin 리뷰 시각에서 옵니다. |
| `mark` | 사람이 적은 경우에만 `전결` 또는 `대결`. 기안 칸에는 적지 않습니다. 전결은 결재 칸 한 칸에만 두며 그 오른쪽 칸은 사선으로 그립니다(검토 칸의 전결은 효력이 없어 사선을 긋지 않고 경고). 추측해서 넣지 않습니다. |
| `reviewer` | Origin 검토자 식별자(이메일, `user_…`, 팀 슬러그). 그 사람이 알려 준 값만 씁니다. 기안 칸에는 두지 않습니다. |

서식마다 쓸 수 있는 칸이 다릅니다. 품의서는 `[기안, 결재]` 두 칸이고 검토 칸을 두지 않는 것이 규칙입니다.

**원칙: 규칙 위반은 경고하고 그대로 렌더하며, 데이터 구조가 깨진 경우에만 거부합니다.**

| 처리 | 경우 |
|---|---|
| 경고 후 렌더(결재 구조, `승인` 대신 `확인 필요`) | 마지막 칸이 결재가 아님, 결재 칸 없음, 검토 칸의 전결(사선을 긋지 않음), 기안자가 검토·결재 칸에도 있음, 한 사람이 두 칸 이상(리뷰는 앞 칸에만 찍힘), 기안자 본인의 리뷰(찍지 않음), 뒤 칸의 가장 이른 승인이 앞 칸의 가장 이른 승인보다 이름(순서 역전, 두 칸 모두 승인 상태일 때, 도장은 그대로) |
| 경고 후 렌더(단순, `승인` 유지) | 기안이 아닌 칸의 `date`(쓰지 않고 리뷰 시각 사용) |
| 경고 후 렌더(미분류, `승인` 유지) | 검토 칸 2칸 이상, 결재 뒤의 검토, 서식에 없는 칸(품의서의 검토), 결재 칸 전결 2칸 이상(첫 전결 칸 기준으로 사선), 기안 칸의 전결·대결(기안 칸 전결로는 사선을 긋지 않음), 기안 칸의 `reviewer`, 결재선에 없는 사람의 `approve`·`request_changes` 리뷰(찍지 않음), main에 머지한 사람이 결재선에 없거나 마지막 칸이 아닌 칸(전결 칸·사선 칸 포함)의 사람이거나 `mergedBy`를 읽지 못함(머지 기록에 그 사람 이름을 적음. 전결이 있을 때 마지막 칸의 사람은 집행이라 경고 없음) |
| 거부 | `approval.steps`가 없거나 목록이 아님, 모르는 필드, 알 수 없는 역할명(옛 `작성`·`승인` 등), `title`·`name` 없음, 첫 칸이 기안이 아니거나 기안이 2칸, 기안 날짜 형식 오류, 알 수 없는 `mark` 값, 형식이 틀린 `sampleMerge` |

경고는 터미널에 `경고: …` 줄로 나오고 한 줄 JSON의 `warnings`에도 담기며, 두 서식(품의서·결과보고서) 모두 문서에도 같은 `경고` 칸으로 인쇄합니다. PDF는 그대로 만들어집니다. 분류(결재 구조·단순)와 원본에 있는 경고 문구는 `rules.json`의 `warnings`에서 읽고, 원본에 문구가 없는 경고만 `approval.py`의 `CODE_TEXTS`에 둡니다. 서식별로 나누지 않습니다. `warnings.draft`는 내부 메모라 문서에 찍지 않습니다. ▲ 분류와 문구는 확정 전 초안입니다. 위반 점검 자체는 품질 검사 몫입니다.

## 기안: 결재 PR 올리기

사람이 데이터 파일을 확인한 뒤에 에이전트가 올립니다.

1. 파일을 저장소 안의 상대 경로에 둡니다. 절대 경로와 토큰은 적지 않습니다.
2. `origin pr create`로 PR을 엽니다. 인증은 환경의 origin CLI가 이미 가진 것을 씁니다.
3. 기안 칸을 빼고 `reviewer`가 있는 칸을 모두 한 번에 검토자로 요청합니다. Origin에는 순차 승인 기능이 없습니다.

```bash
origin pr reviewer request <PR번호> -r <식별자> -r <식별자>
```

4. 기안한 에이전트는 `origin pr review --approve`, `origin pr review --request-changes`를 하지 않고, main으로 `origin pr merge`를 하지 않습니다. 머지는 위의 머지 권한을 따릅니다.

## 검토·결재: 리뷰를 결재란으로 읽기

렌더할 때 `--pr <번호>`를 주면 `origin pr view <번호> --json reviews`로 리뷰를 읽습니다.

1. `approve`, `request_changes` 리뷰만 셉니다. `comment`와 철회(`dismissal`)된 리뷰는 세지 않습니다.
2. 리뷰 작성자의 이름·이메일·핸들·id가 칸의 `name` 또는 `reviewer`와 같으면 그 칸에 연결합니다. 같은 칸에 여러 번이면 가장 늦은 리뷰를 씁니다. 한 사람이 두 칸에 있으면 리뷰는 앞 칸에만 연결합니다(경고). 기안자 본인의 리뷰는 연결하지 않습니다(경고).
3. 연결된 칸에는 이름, KST 날짜, `승인` 또는 `반려`를 찍습니다.
4. 머지 기록은 아래 "머지 기록"을 따릅니다(품의서·결과보고서).

## 반려 뒤: 같은 PR에 이어 고치기

▲ 초안입니다. 문서번호와 결재 상태를 PR 하나에서 정하는 규칙에서 옮긴 절차이며, 확정 전입니다.

▲ 서버 기안 API로 연 문서는 PR을 연 뒤 커밋을 더할 경로가 없어 아직 이 절차를 쓸 수 없습니다.

1. 반려(`request_changes`)나 코멘트로 수정 요청을 받으면, 기안자는 새 PR을 열지 않고 같은 PR의 같은 브랜치에 고친 커밋을 더합니다. 문서번호가 PR 번호라서(아래 "문서번호") 새 PR을 열면 번호와 결재 기록이 두 PR로 갈라집니다.
2. 결재란은 그 PR의 리뷰만 읽고 칸마다 가장 늦은 리뷰를 쓰므로, 반려한 검토자·결재자가 같은 PR에서 다시 승인하면 그 칸의 `반려`가 `승인`으로 바뀝니다.
3. ▲ 고치기 전의 승인은 이전 내용 기준입니다. 결재란의 `승인` 표시는 리뷰를 커밋과 묶지 않고 읽으므로(`approval.py`의 `latest_decisions`), 고친 커밋을 더해도 고치기 전에 승인한 칸은 `승인`으로 남습니다.
4. 그래서 고친 뒤에는 반려한 칸만이 아니라 이미 승인하거나 반려한 모든 칸에 위 "기안" 3번의 `origin pr reviewer request`로 다시 검토를 요청합니다. 기안자는 이때도 리뷰를 제출하지 않습니다.
5. 기안자는 그 모든 칸에서 마지막으로 고친 커밋 뒤의 새 리뷰가 올 때까지 머지 준비가 끝났다고 말하지 않습니다. 결재란과 결재 상태가 `승인`으로 보여도 같습니다.
6. 기안자는 새 세션이 이어받을 수 있게 PR 본문이나 코멘트에 다음을 남깁니다. 비밀·토큰은 적지 않습니다.
   - 현재 상태: 결재 상태, 현재 차례, 마지막으로 고친 커밋, 그 커밋 뒤의 새 리뷰가 아직 없는 칸
   - 남은 지적: 아직 고치지 않은 반려·수정 요청
   - 결정된 사항: 검토자·결재자가 리뷰·코멘트로 정한 것
7. 이어받은 세션은 새 PR을 열기 전에 그 기록과 PR의 리뷰를 읽고 같은 브랜치에서 이어 씁니다. 새 PR은 이미 머지된 문서를 고칠 때만 열고, 그 문서의 원래 문서번호를 그대로 둡니다(운영규칙 1.2.1 6항).

## 머지 기록

전결은 관례대로 결재 칸에 `전결`을 적고 그 오른쪽 칸을 사선으로 긋습니다. 전결 칸의 사람은 승인 리뷰(`approve`)로 결정합니다. 그 칸의 이름·날짜·`승인`은 이 리뷰에서만 나오고, 리뷰가 없으면 `전결`만 찍힙니다. main 머지는 전결이 있어도 마지막 칸의 사람이 하며, 이것을 집행으로 적습니다.

```json
{"role": "결재", "title": "전결자", "name": "최민수", "mark": "전결"},
{"role": "결재", "title": "최종 결재자", "name": "김가상"}
```

머지한 사람과 머지한 브랜치는 추측하지 않고 Origin 기록에서 읽습니다. `--pr`를 주면 `origin pr view <번호> --json mergedAt,mergedBy,baseRefName`의 `mergedBy`(`id`, `displayName`)를 칸의 `name`·`reviewer`와 맞추고, `baseRefName`으로 main 머지와 취합을 나눕니다. `--pr`가 없을 때는 예시용 `sampleMerge`(`{"mergedAt": …, "mergedBy": {"displayName": …}, "baseRefName": …}`, `sampleReviews`처럼 실제 파일에는 넣지 않음)를 씁니다. `baseRefName`이 없으면 main 머지로 봅니다.

| 경우 | 머지 기록 위치와 표기 |
|---|---|
| 머지 전 | 결정 칸(결재 칸의 전결 칸, 없으면 마지막 칸) 아래 `merge 대기` |
| 전결 없이 마지막 칸의 사람이 머지 | 마지막 칸 아래 `10/31 merge` |
| 전결이 있고 마지막 칸의 사람이 머지 | 전결 칸 아래 `집행: 이름 10/31`. 사선 칸에는 아무것도 적지 않음 |
| `stage/*` 브랜치로 머지(중간 머지) | 결재란 밖, 표 아래에 `취합: 이름 10/31 (stage/…)`. `승인`이 아니며 결재 상태를 바꾸지 않음 |
| 마지막 칸이 아닌 사선 칸의 사람이 main에 머지 | 전결 칸 아래 `머지: 이름 10/31`(사선 칸에는 글자를 적지 않음), 경고 |
| 전결 칸, 또는 사선이 없는 칸 중 마지막 칸이 아닌 칸의 사람이 main에 머지 | 그 칸 아래 `머지: 이름 10/31`, 경고 |
| 결재선에 없는 사람, `mergedBy`를 못 읽음 | 결정 칸 아래 `머지: 이름 10/31`(못 읽으면 `미확인`), 경고 |

`집행`과 `취합` 표기, 취합으로 보는 브랜치 접두어(`stage/`)는 원본에 아직 없어 `approval.py`의 `CODE_NOTES`·`COLLECT_BRANCH`에 둡니다. 원본 `mergeNote`에 들어오면 사본으로 옮깁니다(아래 '규칙 단어 바꾸기').

## 결재 상태와 현재 차례

결재 상태는 파일에 적지 않고 리뷰에서 계산합니다. 단어는 `rules.json`의 `approvalStatus`(`진행`, `반려`, `승인`, `확인 필요`)에서 읽습니다. ▲ `확인 필요`는 확정 전 초안이고 판정 `▲ 확인 필요`와 단어가 겹칩니다.

1. 기안 칸은 이미 기안한 칸입니다.
2. 결재 칸 전결의 오른쪽 칸은 차례에서 뺍니다.
3. 왼쪽부터 보아 승인 리뷰가 없는 첫 칸이 현재 차례이고, 결재 상태는 `진행`입니다.
4. 그 칸의 최신 리뷰가 `request_changes`이면 결재 상태는 `반려`, 현재 차례는 기안자입니다.
5. 결재 칸이 1칸 이상 있고 기안 외 모든 칸(전결 칸 오른쪽 칸 제외)이 승인이면 결재 상태는 `승인`, 현재 차례는 없습니다.
6. 결재 칸이 없는데 남은 칸이 모두 승인이거나, 5의 조건이 맞아도 결재 구조 경고가 있으면 `승인` 대신 `확인 필요`로 보이고 문서 `경고` 칸에 이유를 인쇄합니다. 단순 경고만 있으면 `승인`을 그대로 둡니다.

결재 상태는 판정과 다릅니다. 판정(`✔ 머지 가능`, `▲ 확인 필요`, `✖ 보류`)은 기안자가 데이터 파일의 `verdict` 필드에 적는 의견이고, 기호와 문구는 `skills/report-format/template/make_report.py`의 `VERDICTS`에 있습니다.

## 문서번호

`{종류}-{기안 연도}-{PR 번호 4자리}`입니다. 예: `품의-2026-0042`, `보고-2026-0042`. 파일에 적지 않고 렌더할 때 `--pr` 또는 `--number`로 받은 PR 번호로 찍습니다. 번호가 없으면 `품의-2026-미부여`로 찍힙니다.

## 규칙 단어 바꾸기

코드는 역할명, 결재 상태 단어, 문서번호 종류, 머지 기록 표기(`merge 대기`, `10/31 merge`, `머지: 이름 10/31`, `미확인`), 경고 분류와 원본에 있는 경고 문구를 `rules.json`에서만 읽습니다. 원본에 아직 없는 `집행`·`취합` 표기만 `approval.py`의 `CODE_NOTES`에 있고, 원본 `mergeNote`에 같은 키가 생기면 `tests/test_rules_sync.py`가 실패해 사본으로 옮기게 합니다. 사본의 `mergeNote.jeongyeolWho`는 원본에 남아 있어 사본에도 두지만 코드는 쓰지 않습니다. `rules.json`은 사본이고 원본은 `operating-rules-config.json`입니다.

1. 원본 `operating-rules-config.json`을 먼저 고칩니다.
2. `rules.json`의 같은 값을 원본에 맞춥니다.
3. `python3 -m pytest tests`로 확인합니다.

`rules.json`만 고치지 않습니다. 키마다 원본 위치는 원본의 `copies["skills/approval-line/rules.json"].map`에 있고, `tests/test_rules_sync.py`가 이 map을 따라 값이 다르거나, 사본에 없거나, map에 없는 값이 사본에 있으면 실패합니다.

map에 없는 원본 값은 사본에 두지 않고 코드가 따릅니다. 같은 테스트가 원본 값이 코드 동작과 같은지 확인하므로, 원본에서 이 값을 바꾸면 테스트가 실패하고 코드를 함께 고칩니다.

| 원본 값 | 코드 |
|---|---|
| `line.firstIsDraft: true` | `approval.check_line`이 첫 칸이 기안이 아니면 거부 |
| `line.maxSteps: null` | 칸 수 상한 검사 없음 |
| `forms.proposal.reviewAllowed: false` | `render_proposal.py`의 `ROLES`(기안, 결재), 검토 칸은 경고 |
| `onViolation` | 규칙 위반은 경고 후 렌더, 구조가 깨진 데이터만 거부 |
| `jeongyeol.afterBoxes: 사선` | `approval.slashed_indexes`가 전결 칸 오른쪽 칸을 사선으로 |
| `jeongyeol.effectiveOn: 결재` | `approval.jeon_index`가 결재 칸 전결만 보고, 검토 칸 전결은 사선 없이 경고 |
| `line.drafterInOtherBox: false` | 기안자가 다른 칸에도 있으면 경고 |
| `line.samePersonInTwoBoxes: false` | 한 사람이 두 칸 이상이면 경고 |
| `line.approveInOrder: true` | `approval.order_warnings`: 두 칸이 모두 승인 상태일 때, 각 칸의 철회되지 않은 approve 중 가장 이른 `submittedAt`을 비교해 뒤 칸 것이 앞 칸 것보다 이르면 경고, 도장은 그대로. 기안 칸과 전결 칸 뒤 칸은 비교하지 않음. 칸에 연결된(가장 늦은) 리뷰로는 비교하지 않음(운영규칙 1.1 '승인 순서'). ▲ '앞 칸'이 바로 앞 칸인지 앞의 모든 칸인지는 미정이고, 코드는 앞의 승인 상태인 칸 모두와 비교 |

원본(`operating-rules-config.json`)이 없는 저장소(예: `skills/`·`tests/`만 옮긴 플러그인 공개 저장소)에서는 동기화 테스트를 건너뜁니다(skipped로 표시). 그 시험은 저장소의 docs 디렉터리 아래에서 원본을 찾습니다. `operating-rules.md`는 있는데 원본만 없으면 원본을 옮긴 것으로 보고 실패합니다.

원본의 경고 문구·분류·상태 단어가 바뀌면 사본 `rules.json`만 다시 맞추면 됩니다. 코드는 값을 사본 한 곳에서만 읽습니다. 순서 역전 기준처럼 동작을 정하는 규칙 문구가 바뀌면 `tests/test_approval_gaps.py`의 규칙 문구 대조 시험이 실패하고, 코드를 함께 고칩니다.

## 흔한 오류

| 메시지 | 고칠 곳 |
|---|---|
| `결재선의 첫 칸만 기안입니다.` (거부) | `steps[0].role`을 `기안`으로, 다른 칸에는 `기안`을 쓰지 않습니다. |
| `경고: 마지막 칸이 검토입니다. …` (PDF는 나옴, `확인 필요`) | 규칙을 맞추려면 마지막 칸 `role`을 `결재`로 합니다. |
| `경고: 검토 칸이 2칸입니다. …` (PDF는 나옴) | 규칙을 맞추려면 검토 칸을 하나만 둡니다. |
| `경고: 검토 칸이 결재 칸 뒤에 있습니다. …` (PDF는 나옴) | 검토 칸을 결재 칸 앞으로 옮깁니다. |
| `경고: 결재 칸의 전결이 2칸입니다. …` (PDF는 나옴) | 전결 `mark`를 결재 칸 한 칸에만 둡니다. |
| `경고: 결재 칸이 없습니다. …` (PDF는 나옴, `확인 필요`) | 마지막에 결재 칸을 둡니다. |
| `경고: 검토 칸(김검토)에 전결 표시가 있습니다. …` (PDF는 나옴, `확인 필요`) | 전결은 결재 칸에 적습니다. 검토 칸의 `mark`를 지웁니다. |
| `경고: 기안자(홍길동)가 최종 결재자 칸에도 있습니다. …` (PDF는 나옴, `확인 필요`) | 기안자가 아닌 사람을 그 칸에 둡니다. |
| `경고: 기안자(홍길동)의 리뷰는 결재란에 찍지 않았습니다. …` (PDF는 나옴, `확인 필요`) | 기안자는 자기 문서에 리뷰를 제출하지 않습니다. |
| `경고: 이가상이(가) 2칸에 있습니다. …` (PDF는 나옴, `확인 필요`) | 한 사람은 한 칸에만 둡니다. 뒤 칸은 리뷰가 찍히지 않아 계속 차례로 남습니다. |
| `경고: 최종 결재자 칸 승인(…)이 앞 결재자 칸 승인(…)보다 이릅니다. …` (PDF는 나옴, `확인 필요`) | 앞 칸부터 승인합니다. 뒤 칸 사람이 다시 승인하면 순서가 맞습니다. |
| `경고: 기안 칸에 전결 표시가 있습니다. …` (PDF는 나옴) | 기안 칸의 `mark`를 지웁니다. |
| `경고: 기안 칸에 reviewer가 있습니다. …` (PDF는 나옴) | 기안 칸의 `reviewer`를 지웁니다. |
| `경고: 이가상 칸에 date가 있습니다. …` (PDF는 나옴) | 기안이 아닌 칸의 `date`를 지웁니다. 날짜는 리뷰 시각에서 옵니다. |
| `경고: 리뷰한 사람(최민수)이 결재선에 없어 결재란에 찍지 않았습니다. …` (PDF는 나옴) | 전결이면 그 사람 칸을 두고 `mark`를 `전결`로 적습니다. `name` 또는 `reviewer`가 Origin 리뷰 작성자와 같아야 합니다. |
